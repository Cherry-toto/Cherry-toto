## 关键环境经验：git push 被 ghfast.top 代理拦截
- 全局 gitconfig 有 `url.https://ghfast.top/https://github.com/.insteadof=https://github.com/`，clone/pull 走镜像加速。
- 但经 ghfast.top 推送会返回 403 "Permission denied"（即便 Token 有 push/admin 权限、main 无分支保护）——该镜像不代理 push。
- 解法：绕过 ghfast，直连 `https://<TOKEN>@github.com./Cherry-toto/Cherry-toto.git`（github.com. 尾点让 insteadOf 不匹配），配合 https.proxy 127.0.0.1:10809，`git ls-remote`/`push` 均成功。已验证 API(200)、ls-remote(成功)、push(成功)。
- 本机 Windows 凭据管理器只有 gitee 凭据，无 GitHub 凭据；无 gh CLI、无 .netrc。Fine-grained PAT 不返回 X-OAuth-Scopes，需看 repo 的 permissions 字段判断 push 权限。

## 后续2：回退 github 官方后仍认证失败 → 根因是 GitHub 不再支持账号密码
- 报错 `remote: Invalid username or token. Password authentication is not supported for Git operations.` + `fatal: Authentication failed for 'https://github.com/...'`。
- 根因：用户手动 push 时把 **GitHub 登录密码** 当 git 密码填；GitHub 自 2021 起对 HTTPS Git 操作**只接受 PAT，不接受账号密码**。与 ssl/代理/分支保护无关。
- 修复：用 `git -c credential.helper=<GCM> credential approve` 把 Fine-grained PAT（`github_pat_...`，对该仓库有 Contents: Read&write）写入 Windows 凭据管理器，target=`git:https://github.com`。写入后 `GIT_TERMINAL_PROMPT=0 git ls-remote origin` 无弹窗即成功返回 refs → 认证通过。TortoiseGit 自动读取该凭据，无需再填。
- 结论：本机 GCM 路径 `/mingw64/bin/git-credential-manager`；凭据存于系统级 WCM（git:https://github.com / git:https://gitee.com），与 git config 无关，TortoiseGit 同样读取。

## 后续3：新 fine-grained Token 推送 403 的完整排查（可复用）
现象：`git push` → `remote: Permission to Cherry-toto/Cherry-toto.git denied to Cherry-toto.` + 403。
逐项排除的干扰项：
1. **URL 格式**：内联 Token 必须写 `https://用户名:TOKEN@host`（带冒号）。写成 `https://TOKEN@host`（无冒号）会被 git 当成「用户名=TOKEN、密码为空」→ 401→403。修正后仍 403，说明不是格式问题。
2. **ghfast.top 镜像**：只读，push 转发到 GitHub 时 GitHub 收到匿名/镜像凭据 → 403。不能用于 push。
3. **10809 代理**：小请求(GET/ls-remote/api)正常，但 push 上传数据包时 HTTP/2 连接被重置(`Connection was reset`)。改 HTTP/1.1 后露出 403；`curl --noproxy '*' github.com` 返回 200，说明沙箱可直连 GitHub（清空 `http.proxy=` 即可直连）。但直连仍 403 → 也不是网络问题。
4. **决定性验证**：`curl -X PUT /repos/Cherry-toto/Cherry-toto/contents/test -H "Authorization: Bearer $TOKEN"` 返回 `403 Resource not accessible by personal access token` → 证明该 Token 对仓库**只有读、无写权限**。
   注意：fine-grained Token 调 `/repos/{o}/{r}` 返回的 `permissions.push=True` 是**账号**权限、不是该 Token 的授权范围，不能据此判断可写；应以实际写操作(API PUT / git push)结果为准。
结论：用户提供的第二个 fine-grained Token 是只读的，无法 push。需用户重新生成具备 **Contents: Read and write** 权限（Repository access 包含本仓库或 All repositories）的 Token。认证通路本身已完全打通，换一个可写 Token 即可立即推送成功。
